Getting Started with NNS: Forecasting

Fred Viole

Forecasting

The underlying assumptions of traditional autoregressive models are well known. The resulting complexity with these models leads to observations such as,

``We have found that choosing the wrong model or parameters can often yield poor results, and it is unlikely that even experienced analysts can choose the correct model and parameters efficiently given this array of choices.’’

NNS simplifies the forecasting process. Below are some examples demonstrating NNS.ARMA and its partial-moment component forecasting method. It does not require a parametric distribution family; predictive assessment still requires a suitable temporal validation design.

Linear Regression

NNS.ARMA has the ability to fit a linear regression to the relevant component series, yielding very fast results. For our running example we will use the AirPassengers dataset loaded in base R.

We will forecast 44 periods h = 44 of AirPassengers using the first 100 observations training.set = 100, returning estimates of the final 44 observations. We will then test this against our validation set of tail(AirPassengers,44).

Since this is monthly data, we will try a seasonal.factor = 12.

Below is the linear fit and associated root mean squared error (RMSE) using method = "lin".

nns_lin = NNS.ARMA(AirPassengers,
               h = 44,
               training.set = 100,
               method = "lin",
               plot = TRUE,
               seasonal.factor = 12,
               seasonal.plot = FALSE)

sqrt(mean((nns_lin - tail(AirPassengers, 44)) ^ 2))
## [1] 35.39965

Nonlinear Regression

Now we can try using a nonlinear regression on the relevant component series using method = "nonlin".

nns_nonlin = NNS.ARMA(AirPassengers,
               h = 44,
               training.set = 100,
               method = "nonlin",
               plot = TRUE,
               seasonal.factor = 12,
               seasonal.plot = FALSE)

sqrt(mean((nns_nonlin - tail(AirPassengers, 44)) ^ 2))
## [1] 17.90252

The plot and RMSE are computed when this vignette is built, using the installed NNS version. They describe this fixed training/test split; historical values are not a performance guarantee.

Cross-Validation

We select the period using only the first 100 observations. Within that training prefix, the first 80 observations fit candidate models and observations 81–100 select the period. The final 44 observations remain untouched until the selected model is evaluated. Known monthly frequency is also a legitimate pre-specified choice; selecting a period on those final 44 outcomes would make their error a tuning score rather than a test score.

training <- head(AirPassengers, 100)
inner_n <- 80L
candidates <- 1:16
seas <- data.frame(
  Period = candidates,
  validation_RMSE = vapply(candidates, function(period) {
    predicted <- NNS.ARMA(head(training, inner_n), h = length(training) - inner_n,
                          method = "lin", seasonal.factor = period,
                          plot = FALSE, seasonal.plot = FALSE)
    sqrt(mean((predicted - tail(training, length(training) - inner_n))^2))
  }, numeric(1))
)
a <- seas$Period[which.min(seas$validation_RMSE)]

This outer test score evaluates one selected procedure. The earlier linear and nonlinear illustrations are separate pre-specified comparisons; choosing among them after seeing their test errors would require a new test period.

Note: You may experience instances with monthly data that report seasonal.factor close to multiples of 3, 4, 6 or 12. For instance, if the reported seasonal.factor = {37, 47, 71, 73} use (seasonal.factor = c(36, 48, 72)) by setting the modulo parameter in NNS.seas(..., modulo = 12). The same suggestion holds for daily data and multiples of 7, or any other time series with logically inferred cyclical patterns. The nearest periods to that modulo will be in the expanded output.

Selecting Seasonal Factors with NNS.ARMA.optim

NNS also offers a wrapper function NNS.ARMA.optim() that searches combinations from a supplied vector of seasonal.factor and returns the selected objective value (in this case RMSE written as obj.fn = expression( sqrt(mean((predicted - actual)^2)) )) and the corresponding periods, as well as the NNS.ARMA regression method used. Alternatively, using external package objective functions work as well such as obj.fn = expression(Metrics::rmse(actual, predicted)).

NNS.ARMA.optim() also compares smoothing the training series, shrinking component forecasts toward their means, and weighting seasonal estimates. The default linear approximation uses the linear search to select seasonal candidates before comparing nonlinear and mixed forecasts. By default it adds no bias shift (bias.correction = "none"); "split" estimates a gravity shift from the first half of the internal validation errors and accepts it on the later half, and bias.validation reports that decision. These are tuning steps within the first 100 observations.

For this monthly series, we specify periods of 12, 18 and 24 months before inspecting the reserved test outcomes. Each leaves at least three observations per phase in the 80-observation inner training window. Longer candidates up to 60 would be removed by the optimizer’s sample-support rule for this window, so the code lists the supported candidates explicitly.

optimizer_periods <- c(12L, 18L, 24L)
nns.optimal <- NNS.ARMA.optim(training,
                              training.set = inner_n, h = 44,
                              seasonal.factor = optimizer_periods,
                              obj.fn = expression(sqrt(mean((predicted - actual)^2))),
                              objective = "min",
                              ncores = 1, print.trace = FALSE,
                              pred.int = .95, plot = TRUE)

The optimizer’s obj.fn describes its final internal validation forecast. The other two scores evaluate the raw forecast and the returned, corrected forecast against the reserved final 44 observations. They are diagnostics; the example does not use them to choose a bias policy. Selecting a policy from these comparisons would require a new chronological test window. All values and the returned forecasts are regenerated at each build. A fitted bias shift is a model parameter, not proof of persistent future bias.

Extension of Estimates

We can forecast another 50 periods out-of-sample (h = 50), using all observations now available as training history. The requested interval level names the residual-quantile construction; future coverage must be assessed separately.

The longer history supports candidate periods through 36 months under the optimizer’s default 80% internal training split. This deployment example has no observed future outcomes to score.

extended <- NNS.ARMA.optim(AirPassengers,
                            seasonal.factor = seq(12, 36, 6),
                            obj.fn = expression(sqrt(mean((predicted - actual)^2))),
                            objective = "min",
                            ncores = 1, print.trace = FALSE,
                            pred.int = .95, h = 50, plot = TRUE)

head(data.frame(horizon = seq_along(extended$results),
                forecast = extended$results,

Brief Notes on Other Parameters

  • seasonal.factor = c(1, 2, ...)

We included the ability to use any number of specified seasonal periods simultaneously, weighted by their strength of seasonality. Computationally expensive when used with nonlinear regressions and large numbers of relevant periods.

  • weights

Instead of weighting by the seasonal.factor strength of seasonality, we offer the ability to weight each per any defined compatible vector summing to 1.
Equal weighting would be weights = "equal".

  • pred.int

Returns lower and upper bands for each forecasted point from a maximum entropy bootstrap of the forecast path, and plots the bootstrapped replicates. The band describes how dispersed the forecast path is, not the probability that future values fall inside it: it does not widen with the horizon and is not calibrated to the nominal level. NNS.ARMA.optim builds its interval from validation errors instead.

  • seasonal.factor = FALSE

We also included the ability to use all detected seasonal periods simultaneously, weighted by their strength of seasonality. Computationally expensive when used with nonlinear regressions and large numbers of relevant periods.

  • best.periods

This parameter restricts the number of detected seasonal periods to use, again, weighted by their strength. To be used in conjunction with seasonal.factor = FALSE.

  • modulo

To be used in conjunction with seasonal.factor = FALSE. This parameter will ensure logical seasonal patterns (i.e., modulo = 7 for daily data) are included along with the results.

  • mod.only

To be used in conjunction with seasonal.factor = FALSE & modulo != NULL. With mod.only = TRUE (default), only periods at multiples of modulo are kept: each detected period is replaced by the multiples of modulo on either side of it (period 7 with modulo = 5 gives 5 and 10). Set mod.only = FALSE to keep the empirically detected periods along with the logical seasonal patterns.

  • dynamic = TRUE

This setting generates a new seasonal period(s) using the estimated values as continuations of the variable, either with or without a training.set. Also computationally expensive due to the recalculation of seasonal periods for each estimated value.

  • plot , seasonal.plot

These are the plotting arguments, easily enabled or disabled with TRUE or FALSE. seasonal.plot = TRUE will not plot without plot = TRUE. If a seasonal analysis is all that is desired, NNS.seas is the function specifically suited for that task.
